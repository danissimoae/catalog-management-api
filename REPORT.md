

**Дисциплина:** Архитектура программных систем  
**Тема:** Разработка REST API для управления каталогом товаров 

## Цель работы

Целью данной лабораторной работы является разработка REST API для управления каталогом товаров с использованием современных технологий и архитектурных подходов. В процессе выполнения работы необходимо было реализовать полноценный веб-сервис с поддержкой базовых CRUD операций, валидацией данных, логированием и автоматическим тестированием.

## Задачи работы

В рамках лабораторной работы были поставлены следующие задачи:

1. Спроектировать и реализовать REST API для управления товарами
2. Реализовать базовые операции создания, чтения, обновления и удаления товаров
3. Добавить поддержку пагинации и фильтрации данных
4. Организовать валидацию входных данных
5. Настроить систему логирования запросов и ошибок
6. Создать документацию API с использованием Swagger
7. Написать автоматические тесты для проверки функциональности
8. Подготовить проект к развертыванию

## Выбор технологий

Для реализации проекта был выбран стек технологий Node.js и Express.js. Node.js обеспечивает высокую производительность за счет асинхронной модели выполнения, что особенно важно для веб-сервисов. Express.js является минималистичным и гибким фреймворком, который предоставляет необходимый набор функций для создания веб-приложений и API.

В качестве хранилища данных было принято решение использовать in-memory структуру данных. Такой подход упрощает развертывание приложения, исключает необходимость настройки внешней базы данных и полностью соответствует требованиям учебного проекта. Для промышленного использования можно легко заменить хранилище на MongoDB или PostgreSQL без изменения бизнес-логики.

Для валидации данных используется библиотека express-validator, которая предоставляет удобный API для проверки и очистки входных данных. Логирование реализовано с помощью Winston - популярной библиотеки, поддерживающей различные уровни логов и транспорты вывода.

Документация API создается автоматически с использованием Swagger, что позволяет разработчикам быстро ознакомиться с доступными endpoints и протестировать их через веб-интерфейс. Для тестирования выбран фреймворк Jest, который обеспечивает простой синтаксис и встроенную поддержку покрытия кода.

## Архитектура приложения

Приложение построено по модульной архитектуре с четким разделением ответственности. Код организован в следующие слои:

**Модели (Models)** содержат логику работы с данными. В нашем случае это класс Product и класс ProductStore, который управляет коллекцией товаров в памяти. Модель инкапсулирует логику создания, поиска, обновления и удаления товаров.

**Контроллеры (Controllers)** содержат бизнес-логику обработки запросов. Контроллер productController получает данные из запроса, вызывает соответствующие методы модели и формирует ответ. Контроллеры не знают о деталях хранения данных и работают только через интерфейс модели.

**Маршруты (Routes)** определяют endpoints API и связывают их с контроллерами. В файле productRoutes описаны все доступные пути, HTTP методы и прикрепленные к ним обработчики. Здесь же подключаются валидаторы для проверки входных данных.

**Middleware** содержит промежуточные обработчики, которые выполняются до основной логики контроллера. Реализованы три middleware: requestLogger для логирования всех запросов, validators для валидации данных и errorHandler для централизованной обработки ошибок.

**Конфигурация (Config)** включает настройки логгера и Swagger документации. Конфигурационные файлы вынесены в отдельную директорию для удобства изменения параметров без правки основного кода.

Такая архитектура обеспечивает высокую модульность кода, упрощает тестирование отдельных компонентов и позволяет легко расширять функциональность приложения.

## Реализация API endpoints

API предоставляет пять основных endpoints для работы с товарами:

**GET /api/products** возвращает список всех товаров с поддержкой пагинации и фильтрации. Можно указать параметры page и limit для постраничного вывода, category для фильтрации по категории, minPrice и maxPrice для фильтрации по диапазону цен, а также search для поиска по названию и описанию товара. В ответе возвращается массив товаров и объект pagination с информацией о текущей странице, общем количестве товаров и страниц.

**GET /api/products/:id** возвращает информацию о конкретном товаре по его идентификатору. Если товар с указанным ID не найден, возвращается ошибка 404.

**POST /api/products** создает новый товар. В теле запроса необходимо передать JSON объект с полями name, description, price, category и stock. Все поля проходят валидацию перед сохранением. При успешном создании возвращается объект созданного товара со статусом 201.

**PUT /api/products/:id** обновляет существующий товар. Можно передать любые поля для обновления, валидация применяется только к переданным полям. Если товар не найден, возвращается ошибка 404.

**DELETE /api/products/:id** удаляет товар по идентификатору. При успешном удалении возвращается пустой объект data. Если товар не найден, возвращается ошибка 404.

Все ответы API имеют единый формат с полем success, указывающим на успешность операции, полем data с результатом и опциональным полем error с описанием ошибки.

## Валидация данных

Валидация входных данных является критически важной частью любого API. В проекте реализована комплексная система валидации с использованием express-validator.

Для товаров проверяются следующие правила: название должно быть непустой строкой длиной до 100 символов, описание - непустой строкой до 500 символов, цена - неотрицательным числом, категория должна быть одним из предопределенных значений (electronics, clothing, food, books, other), количество на складе должно быть неотрицательным целым числом.

При создании товара все поля обязательны, при обновлении можно передать только те поля, которые нужно изменить. ID товара в URL также валидируется на корректность формата.

Если валидация не проходит, API возвращает ошибку 400 с детальным описанием всех проблем. Это позволяет клиенту сразу понять, какие данные были переданы некорректно и как их исправить.

## Обработка ошибок и логирование

В приложении реализована централизованная обработка ошибок через middleware errorHandler. Все ошибки, возникающие в контроллерах, передаются в этот обработчик через функцию next. Обработчик определяет тип ошибки и формирует соответствующий ответ с корректным HTTP статусом.

Логирование реализовано на двух уровнях. Middleware requestLogger логирует каждый входящий запрос с информацией о методе, URL, статусе ответа, времени выполнения и IP адресе клиента. Это позволяет отслеживать активность API и выявлять проблемы производительности.

Обработчик ошибок логирует все возникающие исключения с полным стеком вызовов. Логи записываются в файлы error.log для ошибок и combined.log для всех событий. В режиме разработки логи также выводятся в консоль с цветовым выделением для удобства отладки.

## Документация API

Документация API создается автоматически с использованием Swagger. В коде маршрутов добавлены JSDoc комментарии с описанием каждого endpoint, параметров запроса, формата тела запроса и возможных ответов.

Swagger UI доступен по адресу /api-docs и предоставляет интерактивную документацию. Разработчики могут не только просмотреть описание API, но и выполнить тестовые запросы прямо из браузера. Это значительно упрощает процесс разработки клиентских приложений и отладки.

В документации описана схема объекта Product со всеми полями и их типами, что позволяет понять структуру данных без изучения исходного кода.

## Тестирование

Для проекта написан набор автоматических тестов с использованием Jest и Supertest. Тесты покрывают все основные сценарии работы API.

Протестировано создание товара с валидными данными и проверка возврата корректного объекта. Также проверяется, что при невалидных данных возвращается ошибка 400. Протестирована работа пагинации, фильтрации по категории и цене.

Для каждого endpoint проверяются как успешные сценарии, так и случаи с ошибками. Например, для получения товара по ID тестируется возврат товара при существующем ID и ошибка 404 при несуществующем.

Перед каждым тестом хранилище данных очищается, что обеспечивает изолированность тестов друг от друга. Тесты можно запустить командой npm test, при этом генерируется отчет о покрытии кода.

## Структура проекта

Проект имеет логичную и понятную структуру. В корне находятся конфигурационные файлы package.json, .gitignore, .env.example, а также документация README.md и LICENSE.

Директория src содержит весь исходный код приложения, разделенный на поддиректории по функциональному назначению. В config находятся настройки, в controllers - контроллеры, в middlewares - промежуточные обработчики, в models - модели данных, в routes - определения маршрутов. Файл index.js является точкой входа в приложение.

Директория tests содержит все тестовые файлы. Такое разделение позволяет легко ориентироваться в коде и быстро находить нужные компоненты.
